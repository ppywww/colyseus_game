# 参考：CS2 持枪视模型 + 沙漠迷城地图 实现规格

> 面向实现者（工程师）。本文所有数值都是**可直接抄进代码的绝对值**，不是"适当调整"。
> 坐标系：右手系，**X 向东（+X）、Z 向南（+Z）、Y 向上**，地面 y = 0。
> 枪模型局部坐标：**−Z 为枪口方向，+X 为右，+Y 为上**（与 three.js 相机默认朝向一致）。

## 1. 调研结论（可验证）

### 1.1 CS2 / CS:GO 第一人称视模型的惯例

| 事实 | 数据 | 对实现的含义 |
| --- | --- | --- |
| 视模型是**独立于世界的一层**，用**独立 FOV** 绘制 | CS2 的 `viewmodel_fov` 当前注册表区间 **60–68**，默认 **60**；CS:GO 时代区间为 **54–68** | 世界 FOV（CS 锁定 90）与武器 FOV 分离，所以枪不会被广角拉变形 |
| FOV 越大，枪越小越远 | 多个来源一致 | 我们主相机 fov 80，若不处理，枪会偏小偏扁 |
| 位置微调只有 3 个轴 | `viewmodel_offset_x` ∈ [−2.5, 2.5]（默认 1）、`offset_y` ∈ [−2, 2]（默认 1）、`offset_z` ∈ [−2, 2]（默认 −1） | 说明"枪在右下、稍微推远、稍微压低"是默认审美 |
| `offset_x` 变大不只是右移，还会**让枪斜置**（"向对角线倾斜"） | 中文攻略对 `viewmodel_offset_x` 的描述 | 金色 AK 在截图里的斜置是刻意结果，必须用 roll（绕枪轴旋转）实现 |
| 视模型遮挡约 1/5 屏幕 | "默认的手臂和武器模型会挡住右侧将近 1/5 的屏幕视野" | 本文方案实测 18.4%，符合 |
| 视模型纯视觉，不影响弹道/命中 | 多来源一致 | 视模型的后坐动画**不得**修改相机 pitch/yaw 的实际瞄准值 |

## 2. 第一部分：持枪视模型规格

### 2.1 层级与坐标约定

```
camera
└── viewModelRoot (Group)      ← 只做动画（呼吸/摆动/后坐/换弹/投掷），位置 = 枪根基准
    ├── gunGroup (Group)       ← 静止姿态，烘焙 (0.05, 0.05, 0.13) 的持枪角
    │   ├── receiver / handguardUp / handguardLow / gasTube / barrel /
    │   │   muzzleBrake / frontSight / rearSight / magazine / magBase /
    │   │   grip / triggerGuard / stock / butt / charging / rail
    │   └── muzzleAnchor (Object3D)  ← 枪口火光与点光源的挂载点（跟着后坐一起动）
    ├── armGroupRight           ← 右手套 + 右前臂
    └── armGroupLeft            ← 左手套 + 左前臂
```

- **枪根** = 机匣后端、握把顶端的交点，即枪模型的 `(0,0,0)`。
- 整枪实测长度：枪托尾 `z = +0.32` 到枪口 `z = −0.575` → **0.895 m**（真枪 AK-47 为 0.870 m，差 3%，可接受）。
- `muzzleAnchor` 必须是 `gunGroup` 的子节点（**不要**挂在 camera 下），这样后坐、换弹、投掷时枪口火光自动跟随。

#### 2.2.1 Capsule 的朝向写法（可直接抄）

`CapsuleGeometry` 默认沿 +Y，需要把它转到"腕 → 肘"方向：

```ts
function limb(from: THREE.Vector3, to: THREE.Vector3, radius: number): THREE.Mesh {
  const dir = new THREE.Vector3().subVectors(to, from);
  const len = dir.length() - radius * 2; // CapsuleGeometry 的 length 不含两端半球
  const mesh = new THREE.Mesh(new THREE.CapsuleGeometry(radius, Math.max(len, 0.01), 4, 8), sleeveMat);
  mesh.position.copy(from).addScaledVector(dir, 0.5);
  mesh.quaternion.setFromUnitVectors(new THREE.Vector3(0, 1, 0), dir.normalize());
  return mesh;
}
```

### 2.3 枪根在相机坐标系中的位置与旋转

#### 2.3.1 参数

| 项 | 值 |
| --- | --- |
| `holder.position` | **(0.2387, −0.228, −0.400)**（替换现有 `(0.24, −0.22, −0.45)`） |
| `holder.rotation` | **(0.05, 0.05, 0.13)**（替换现有 `(0,0,0)` + 每帧覆盖） |

三个角的含义（务必理解，否则改一个就崩）：

| 角 | 值 | 视觉作用 |
| --- | --- | --- |
| `rotation.x = +0.05`（约 2.9°） | 枪口**微微抬起** | 让枪口不显得"戳地"；同时是后坐动画的基准值 |
| `rotation.y = +0.05`（约 2.9°） | 枪口**微微向左** | 让枪口落点靠近屏幕中线，而不是贴着右边缘 |
| `rotation.z = +0.13`（约 7.4°） | 枪身绕枪轴**向右滚转**（顶部倒向左侧） | **这就是 CS 截图里"枪身斜置"的来源**。7–8° 是"能看出来但不过分"的区间；`< 0.08` 看不出来，`> 0.18` 会显得枪要掉了 |

> 参考实现里 `holder.rotation` 被 `update()` 每帧覆盖成 `(recoilRotation − reloadTilt, 0, reloadTilt*0.4)`，这会把上面的静态姿态吃掉。**必须改成"静态基座 + 动画增量"**：`holder.rotation.set(BASE.x + dx, BASE.y + dy, BASE.z + dz)`。

#### 2.3.2 为什么这样摆才像截图（构图判据）

不要靠肉眼调，用下面 3 条判据，全部可量化验证：

| 判据 | 目标值 | 实测（16:9，fov 80） |
| --- | --- | --- |
| ① 枪根（握把）落在屏幕右下角 | 横向 68%–72%、纵向 82%–88% | **(70.0%, 84.0%)** ✓ |
| ② 枪口在屏幕中线右侧、画面中线略下方 | 横向 54%–59%、纵向 57%–63% | **(57.1%, 60.4%)** ✓ |
| ③ **枪管轴线在屏幕上的延长线必须穿过准心**，误差 ≤ 2% | x ∈ [48%, 52%]（y = 50% 处） | **51.2%** ✓ |
| ④ 视模型遮挡屏幕面积 | 15%–22% | **18.4%** ✓ |

判据 ③ 是"看起来像 CS"最关键的一条：如果枪管延长线偏到 60% 或 45%，玩家会觉得"枪不是对着准星的"，非常出戏。

**验证公式**（工程师可以写个单测）：

```
tanV = tan(fov/2)，tanH = tanV × aspect
screenX = 0.5 + (v.x / (−v.z × tanH)) × 0.5
screenY = 0.5 − (v.y / (−v.z × tanV)) × 0.5
其中 v = holder.position + R(holder.rotation) × 部件局部坐标
```

### 2.4 视模型 FOV：两方案与取舍

#### 方案 A（**推荐**）：单 pass，沿用主相机 fov 80

`camera.add(holder)`，不做任何渲染管线改动，直接用 2.3 的数值。

| 优点 | 缺点 |
| --- | --- |
| 零架构改动，现有 `CombatEffects.muzzle`（本来就在 camera 下）无需迁移 | 广角下枪身边缘有轻微透视拉伸 |
| 不存在"视模型被墙穿模 / Z-fighting"问题需要处理 | 换成超宽屏时构图偏移（见 2.3.3） |
| 一次 draw call 管线，无双 pass 的 resize/DPR 同步风险 | 与 CS 的"窄 FOV 视模型"观感差一截 |

**为什么本项目可以接受**：视模型最近点在 `z = −0.323`，远于主相机 `near = 0.1`；场景雾 `near = 25`，对视模型完全无影响；视模型 `castShadow = false`，不参与阴影。广角畸变是唯一代价，且 fov 80 时枪身边缘（屏幕 x > 85%）才明显。

#### 方案 B：双 pass，独立 `Scene` + 独立 `PerspectiveCamera`，fov 62

```ts
// 初始化
this.vmScene = new THREE.Scene();
this.vmCamera = new THREE.PerspectiveCamera(62, aspect, 0.01, 5);
this.vmScene.add(this.vmCamera);
this.vmCamera.add(this.holder);
this.holder.position.set(0.2387, -0.228, -0.5586); // 注意 z 被放大
// 光照：视模型 scene 里补一盏与主场景同向的 DirectionalLight + HemisphereLight，否则枪是全黑的

// 每帧渲染
renderer.render(this.scene, this.camera);   // 世界
renderer.autoClear = false;
renderer.clearDepth();                       // 关键：清深度，否则枪被墙裁掉
renderer.render(this.vmScene, this.vmCamera); // 视模型
renderer.autoClear = true;
```

**参数换算说明（必须照做，否则构图全变）**：
fov 从 80 收到 62 后，同一位置的物体在屏幕上放大 `tan40°/tan31° = 1.3965` 倍。
要让**枪根仍落在 70%/84%**，只需把 `holder.position.z` 乘 1.3965：`−0.400 × 1.3965 = −0.5586`，`x/y` 保持不变。此时其他参考点的偏差 ≤ 4%（枪口变 58.5%/62.5%，左手变 61.4%/74.4%，可接受）。
**不要**试图"整体放大 1.3965 保持原构图"——均匀缩放对屏幕比例是不变的，那样只会让枪大 1.4 倍。

| 优点 | 缺点 |
| --- | --- |
| 得到 CS 的窄 FOV 厚重视感 | 枪口火光的 Sprite 与点光源要跨两个 scene（建议：Sprite 放 `vmScene` 跟随枪，`PointLight` 留在主 scene 照亮环境） |
| 之后加 ADS / 检视动画时不受世界 FOV 干扰 | `muzzleLight` 照亮墙面必须在主 scene，需要两处同步坐标 |

**决策建议**：第一版走方案 A（风险最低、验收快）。方案 B 作为"如果观感不满意"的后手，参数已备好，切换成本约 20 行。

### 2.5 动画状态表

所有动画都是**叠加式**：最终 `holder.position = BASE + Σ(增量)`，`holder.rotation = BASE_ROT + Σ(增量)`。
`BASE = (0.2387, −0.228, −0.400)`，`BASE_ROT = (0.05, 0.05, 0.13)`。

#### 2.5.1 idle 呼吸

| 参数 | 值 |
| --- | --- |
| 周期 | 4.0 s（角频率 ω = 1.571 rad/s） |
| 垂直位移 | `dy = sin(t × 1.571) × 0.0040` → **±4 mm** |
| 水平位移 | `dx = sin(t × 0.785) × 0.0025` → **±2.5 mm**（半频，与 dy 形成李萨如轨迹，避免"直线上下"的机械感） |
| pitch | `+sin(t × 1.571) × 0.0040`（±0.23°） |
| roll | `+sin(t × 0.785 + 1.2) × 0.0060`（±0.34°） |
| 相位 | dy 与 dx 保持 90° 相位差；roll 再额外偏移 1.2 rad |

幅度上限校验：位移幅度 ≤ 5 mm、角度 ≤ 0.35°，超出会让准心"呼吸"到影响瞄准。

#### 2.5.2 walk 摆动（bob）

| 参数 | 值 |
| --- | --- |
| 相位推进 | `bobPhase += dt × 9.0`（走）／`dt × 0`（停）；sprint 时 `× 12.0` |
| 水平 | `dx = sin(bobPhase) × 0.0100` → **±10 mm**（8 字形的横向分量） |
| 垂直 | `dy = −|cos(bobPhase)| × 0.0120` → **0 ~ −12 mm**（取绝对值，保证是"每步一次下沉"而不是双向振荡） |
| 前后 | `dz = sin(bobPhase × 2) × 0.0060` → **±6 mm** |
| roll | `+sin(bobPhase) × 0.0200`（±1.15°），符号与 dx 同相 |
| yaw | `+sin(bobPhase × 0.5) × 0.0120`（±0.69°） |
| 摆幅淡入淡出 | `amp = lerp(amp, moving ? 1 : 0, 1 − exp(−dt / 0.12))`，所有摆幅乘 `amp`。**必须有**，否则停走瞬间枪会"跳"一下 |
| 落地冲击 | 若本帧 `grounded` 由 false 变 true 且上一帧 `vy < −6`：叠加 `dy −= 0.020`，然后以 τ = 130 ms 指数回弹 |

#### 2.5.3 fire 后坐

| 参数 | 值 |
| --- | --- |
| 位移 | 沿 **+Z 后退 0.045 m**（`dz += 0.045`） |
| pitch | `+0.055 rad`（枪口上跳 3.15°） |
| roll | `± 0.012 rad` 随机（每发重新取，制造"连发不重复"） |
| yaw | `± 0.008 rad` 随机 |
| 回弹时间常数 | 位置 τ = **90 ms**（`offset *= exp(−dt/0.090)`）；角度 τ = **110 ms** |
| 回到 5% 所需时间 | 位置 ≈ 270 ms，角度 ≈ 330 ms |
| 连发累加上限 | `dz ≤ 0.080`，`pitch ≤ 0.100`（防止长按把枪顶出画面） |
| 与相机的关系 | **只改视模型**，不改 `camera.rotation`。相机后坐由现有 `this.shake` 独立负责，不要叠加两次 |

#### 2.5.4 reload 换弹（总时长 = `WEAPON_RELOAD_MS` = 1800 ms）

用**关键帧 + smoothstep 插值**实现，不要用三角函数（不可控）。`p` = 归一化进度 0→1。

| 阶段 | p 区间 | 动作 |
| --- | --- | --- |
| 入位下压 | 0.00 – 0.15 | pitch `−0.30 rad`（枪口下垂 17°）、roll `+0.55 rad`（枪身右倾）、`dy −0.10`、`dz +0.06` |
| 卸弹匣 | 0.15 – 0.35 | 保持上阶段姿态；`magazine.position.y` 从 −0.100 → −0.260（沿 −0.22 rad 的倾斜轴下坠），同时 `magazine.rotation.x` 从 −0.22 → −0.38 |
| 插新弹匣 | 0.35 – 0.55 | `magazine.position.y` 从 −0.260 → −0.100；在 p = 0.50 时**过冲**到 −0.085 再回（60 ms 阻尼振荡，用 `−0.015 × sin(π × (p−0.5)/0.05)` 近似） |
| 回抬 + 拉机柄 | 0.55 – 0.80 | 姿态回到中性；`charging.position.z` 从 −0.050 → −0.010 → −0.050（后拉 40 mm 再回，用两段 lerp） |
| 收尾缓冲 | 0.80 – 1.00 | 全部归零；末 80 ms 追加 `dy −0.006` 的下沉再回弹 |

幅度建议不要加大：`pitch −0.30 / roll +0.55` 已经能覆盖屏幕右下 1/4，再大就会挡住准心。

#### 2.5.5 throw 投掷（总时长 = `THROW_COOLDOWN_MS` = 700 ms）

| 阶段 | 时间 | 动作 |
| --- | --- | --- |
| 甩出 | 0 – 180 ms | `dx −0.10`、`dy −0.12`、`dz +0.05`；`rot.z −0.35`、`rot.x +0.30`（枪身向左下甩） |
| 空手停顿 | 180 – 420 ms | 保持甩出姿态，叠加 `sin(t×20) × 0.004` 的轻微抖动（表现"手在掏下一颗"） |
| 回位 | 420 – 700 ms | smoothstep 回 0 |

#### 2.5.6 可选加分项（P1，不影响验收）

转向惯性滞后：`dYaw = yaw_now − yaw_prev` 时，`dx += clamp(−dYaw × 0.020, −0.012, +0.012)`，`rot.z += clamp(−dYaw × 0.030, −0.020, +0.020)`，τ = 140 ms。这一条让"甩枪"有重量感，是 CS 手感的关键之一。

#### 2.5.7 动画更新骨架（可直接抄）

```ts
public update(dt: number, moving: boolean, grounded: boolean, reloadProgress = 0, throwProgress = 0): void {
  const t = (this.clock += dt);

  // ---- idle ----
  let dx = Math.sin(t * 0.785) * 0.0025;
  let dy = Math.sin(t * 1.571) * 0.0040;
  let dz = 0;
  let rx = Math.sin(t * 1.571) * 0.0040;
  let ry = 0;
  let rz = Math.sin(t * 0.785 + 1.2) * 0.0060;

  // ---- walk ----
  this.amp += (Number(moving) - this.amp) * (1 - Math.exp(-dt / 0.12));
  if (moving) this.bobPhase += dt * 9.0;
  const a = this.amp;
  dx += Math.sin(this.bobPhase) * 0.0100 * a;
  dy += -Math.abs(Math.cos(this.bobPhase)) * 0.0120 * a;
  dz += Math.sin(this.bobPhase * 2) * 0.0060 * a;
  rz += Math.sin(this.bobPhase) * 0.0200 * a;
  ry += Math.sin(this.bobPhase * 0.5) * 0.0120 * a;

  // ---- fire recoil ----
  this.recoilPos *= Math.exp(-dt / 0.090);
  this.recoilRot *= Math.exp(-dt / 0.110);
  dz += this.recoilPos;
  rx += this.recoilRot;
  rz += this.recoilRoll;   // 开火时随机赋值，同样指数衰减

  // ---- reload ----
  if (reloadProgress > 0) { /* 按 2.5.4 关键帧表求值并累加 */ }

  // ---- throw ----
  if (throwProgress > 0) { /* 按 2.5.5 三段求值并累加 */ }

  this.holder.position.set(BASE.x + dx, BASE.y + dy, BASE.z + dz);
  this.holder.rotation.set(BASE_ROT.x + rx, BASE_ROT.y + ry, BASE_ROT.z + rz);
}

public recoil(): void {
  this.recoilPos = Math.min(this.recoilPos + 0.045, 0.080);
  this.recoilRot = Math.min(this.recoilRot + 0.055, 0.100);
  this.recoilRoll = (Math.random() - 0.5) * 0.024;
}
```

**为什么是 64 m 而不是 Dust II 的 104 m**：
1. `WEAPON_RANGE = 60`，104 m 的图上超过一半的交火会被射程裁掉；
2. `ARENA_RADIUS = 30`，服务端 `transform.ts` 已按 `±30` 逐轴 clamp，直接用 ±30 做可玩区可以**零改动**保持同步；
3. 缩放比 60 / 104 ≈ **0.58**。对照真实枪线：Pit → A 坡道 53.6 m × 0.58 ≈ **31 m**，本文 A 点内最长通视 16.3 m、中门 31.3 m，比例吻合。

### 3.6 可跳越高度规范

依据：`jumpSpeed = 7.5 m/s`、`gravity = 22 m/s²` → 跳跃最高点 `h_max = 7.5² / (2 × 22) = **1.278 m**`（与 CS 的 42–45 u ≈ 1.07–1.14 m 同量级，略高，符合"浏览器 FPS 更好上手"的取向）。

| 高度区间 | 判定 | 设计含义 |
| --- | --- | --- |
| 0.6 – **1.15 m** | **可跳上**（含 20 cm 余量：1.278 − 1.15 ≈ 0.13） | 半身箱 / 沙袋 / 平台。跳上去能获得视野优势，但站在上面是完全暴露的 |
| 1.16 – 1.30 m | **灰区，禁止使用** | 会表现成"跳一半被推开"的黏滑手感，玩家会认为有 bug |
| 1.31 – 1.55 m | **不可跳** | 视觉上像"应该能跳"，实际不能 → 不要用这个高度 |
| **≥ 1.6 m** | **不可跳，明确墙体** | 全身箱 / 高墙。玩家一眼就知道要绕 |

补充：
- **不要放 0.2 – 0.45 m 的台阶**：`stepPlayer` 没有 step-up 逻辑，这种高度会被当成立墙，造成"卡在台阶前"的糟糕体验。要么 0（平地），要么 ≥ 0.6 m（可跳）。
- 站在 1.1 m 箱子上时相机眼高 = 1.1 + 1.6 = 2.7 m，可以越过 2.4 m 的墙（`L4 拐角墙`）看到后面的走位——这是刻意保留的信息差设计。

### 3.9 与现有系统的接口约束

#### 3.9.1 硬约束：只能轴对齐（AABB）

**不允许任何旋转体**。原因：服务端弹道遮挡（`apps/server/src/rooms/combat.ts` 用 `obstacleColliders()` 做射线-AABB 求交）和客户端物理（`resolveBox()` 做 MTA 推出）都只认 AABB。
- 斜墙 → 用**台阶状拼接**（例如 A 小道的拐角用 2–3 段正交短墙拼）；本规格的 25 段墙已经全部是正交的。
- 拱门 → 用两根方柱 + 一根不加碰撞的视觉横梁（横梁不写进 `OBSTACLES`）。
- 棕榈树/油桶 → 用包围方柱（0.6×0.6、1.1×1.1），不做圆柱碰撞。
- 推车 → 用一个整箱覆盖车体（轮子伸出车体一部分，但**不单独加碰撞**，避免玩家卡在轮子与车板之间）。

#### 3.9.2 数据接口

建议把 `ObstacleSpec` 扩展为（新增 `type` 字段用于渲染分派，不动 `color`）：

```ts
export type ObstacleKind = "wall" | "crate" | "cart" | "arch" | "palm" | "barrel" | "sandbag";

export interface ObstacleSpec {
  x: number; z: number;
  width: number; height: number; depth: number;
  color: number;
  type: ObstacleKind;   // 新增
}
```

`obstacleColliders()` 不需要改（它只读 x/z/width/height/depth）。

## 4. 实现顺序与风险

### 4.1 建议实现顺序（每步都能独立验收）

1. `packages/shared`：新增 `MAP_BOUNDS` / `MAP_SIZE` / `ObstacleKind`，替换 `OBSTACLES` 为 64 条 → `pnpm typecheck` 通过。
2. 三处圆形钳制改矩形（`player-physics.ts`、`throwables.ts`、`grenades.ts`），跑现有单测 → 玩家能走到地图四角不被拽回。
3. `map.ts` 重写 `buildArena()` + `game.ts` 的雾/背景/灯光 → 能跑起来，能在地图里走一圈（此时枪还是旧的）。
4. `viewmodel.ts` 重建 25 个部件 + 静态构图 → 对照 2.3.3 校准表逐项核对（枪根 70%/84%，枪口 57%/60%）。
5. 动画：idle → walk → fire → reload → throw，逐个加。
6. `effects.ts` 枪口位置与尺寸对齐 → 开火火光出现在枪口帽正前方。
7. 服务端 `nextSpawnPoint()` 换成固定出生表。

### 4.2 我判断的最大实现风险（按严重度排序）

| 风险 | 症状 | 规避 |
| --- | --- | --- |
| **① 圆形钳制未全部改矩形** | 玩家走到地图四角时被"吸"向中心；服务端与客户端位置不一致导致橡皮筋 | 三处（客户端 2 + 服务端 1）必须同时改，`transform.ts` 不用改。改完用"走到 (29,29)"作为验收用例 |
| **② `holder.rotation` 每帧被覆盖** | 静态的 7.4° 斜置姿态被吃掉，枪永远是正的，怎么调参数都不像截图 | 2.3.1 的警告：拆成 `BASE_ROT + 增量` |
| **③ 64 个 AABB 的性能与观感** | 每个 Box 单独一个 Mesh + Material → 64 次 draw call；用 `EdgesGeometry` 描边会翻倍到 128 次 | 按 `type` 复用 6–7 个共享 `Material`（不要每个箱子 new 一个）；去掉蓝色描边（那是赛博风格，与沙漠不符）；`castShadow` 只给高度 ≥ 1.4 m 的物件开 |
| **④ 出生点仍在墙里** | 开局卡在建筑体块内（W2 是 12×24 的实心块，最容易踩坑） | 用 3.7 的表；落地后用 3.10 的洪水填充脚本复核 |
| **⑤ 掩体高度落在 1.16–1.55 m 灰区** | 玩家在箱子前反复跳、觉得"跳不上去是 bug" | 只用 ≤ 1.15 m 与 ≥ 1.6 m 两档；本文 39 个掩体已按此分档 |
| **⑥ 视模型被雾/近平面裁切** | 换沙漠配色后枪变灰或被切掉一角 | 雾 `near = 40`（视模型最远 0.97 m，无影响）；`near = 0.1` 保持不变 |

# 服务端技术选型与架构设计

> 状态：现有技术基线已从仓库代码确认；扩展方案与尚未验证的基础设施均标记为“待确认”。本文不是开发完成声明。

## 1. 目标与选型原则

服务端固定采用 **Node.js + TypeScript + Colyseus**，不考虑替换为其他多人游戏服务端框架。后续工作以现有代码为基础逐步完善，优先保证实时对战的稳定性、状态一致性、可维护性和可扩展性。

## 2. 当前代码已确认的技术栈

| 层级 | 当前技术 | 代码依据 / 用途 | 状态 |
|---|---|---|---|
| 运行环境 | Node.js | 运行服务端进程 | 已使用 |
| 开发语言 | TypeScript | 服务端与共享协议代码 | 已使用 |
| 多人游戏框架 | Colyseus（0.16 系列） | 房间生命周期、客户端会话和状态同步 | 已使用，确定保留 |
| 网络传输 | `@colyseus/ws-transport` | WebSocket 实时连接 | 已使用 |
| 状态同步 | Colyseus Schema | 玩家与战斗状态同步 | 已使用 |
| 数据校验 | Zod | 配置或消息数据校验 | 已使用 |
| 日志 | Pino | 服务端日志记录 | 已使用 |
| 包管理 / 工程组织 | pnpm workspace | 多包 Monorepo | 已使用 |
| 共享代码 | `packages/shared` | 客户端与服务端共享类型、常量和协议 | 已使用 |

服务端入口通过 `Server`、`WebSocketTransport` 创建游戏服务器，并注册 `FPSBattleRoom` 房间类型。核心实现位于 `apps/server`。

## 3. 服务端模块现状

仓库中已存在以下模块或文件：

- 房间：`apps/server/src/rooms/fps-battle-room.ts`
- 战斗处理：`rooms/combat.ts`
- 投掷物：`rooms/grenades.ts`
- 近战：`rooms/melee.ts`
- 出生点：`rooms/spawn.ts`
- 变换 / 位置相关：`rooms/transform.ts`

以上说明仓库已有战斗与房间逻辑基础；文件存在不等于所有网络边界情况、权威判定和性能目标已经满足。

## 4. 服务端职责边界

服务端应逐步承担并验证以下职责：

1. 房间创建、加入、离开、销毁及房主权限。
2. 玩家身份、队伍、角色和房间规则校验。
3. 对关键游戏结果进行服务端权威判定，例如伤害、命中、死亡、复活、计分和胜负。
4. 管理需要同步的权威状态，并通过 Colyseus Schema 向客户端广播。
5. 校验客户端输入，限制非法状态变更和异常消息。
6. 记录必要日志、异常和关键对局事件。

客户端可以负责输入采集、画面表现、预测和插值；不能仅凭客户端上报结果决定关键战斗结算。

## 5. 实时网络与同步策略

### 5.1 已有基础

- Colyseus 房间与 WebSocket 传输已接入。
- 使用 Schema 表达并同步部分游戏状态。
- 客户端已有插值相关模块，服务端已有位置 / 变换相关模块。

### 5.2 需要结合实测完善

- 服务端模拟 / 状态更新频率。
- 状态同步字段范围与频率，避免无意义的高频广播。
- 客户端插值、必要的预测与纠正。
- 延迟、抖动、丢包和短暂断线的处理。
- 命中判定是否需要历史状态与延迟补偿，以及其公平性边界。
- 重连、超时、房间销毁和异常玩家清理。

具体 tick rate、同步频率和延迟补偿算法均待压测与玩法规则确认，不在此提前写死数值。

## 6. 数据持久化与基础设施

目前已检查的代码尚不足以确认项目已接入数据库或 Redis，因此先不把它们列为现有依赖。

| 能力 | 当前结论 | 后续判断依据 |
|---|---|---|
| 数据库 | 待确认 / 尚无已验证结论 | 是否需要账号、长期战绩、排行榜、玩家设置持久化 |
| Redis / 缓存 | 待确认 / 尚无已验证结论 | 是否需要跨进程房间协调、分布式 presence 或共享缓存 |
| 部署平台 | 待确认 | 并发规模、区域、运维能力和预算 |
| 监控与告警 | 待确认 | 在线人数、房间数、延迟、错误率和资源使用情况 |
| 数据备份 | 待确认 | 持久化数据种类与恢复目标 |

不要仅因为使用 Colyseus 就默认必须引入 Redis 或数据库；先明确产品需求和部署拓扑，再决定。

## 7. 安全与稳定性要求

- 服务端校验房间操作、队伍切换、开始游戏等权限。
- 对客户端消息做结构、范围、频率和状态合法性校验。
- 对聊天等用户输入进行长度限制与内容安全处理。
- 防止客户端伪造伤害、位置、计分和胜负结果。
- 为断线、重连、超时和异常退出定义明确状态流转。
- 记录可用于排查问题的结构化日志，避免记录敏感信息。

## 8. 与资源加载系统的边界

游戏资源（模型、贴图、地图文件、动画、音效）不应通过 Colyseus 实时状态同步通道传输。建议由客户端资源系统通过 HTTP(S) 获取，并结合静态资源托管 / CDN、浏览器缓存和预加载策略。

Colyseus 主要负责房间和实时游戏数据；资源文件分发属于 Web 静态资源链路。服务端可以提供资源清单或版本信息，但不应把大体积资源作为实时房间消息发送。

## 9. 后续需要确认的决策

- 服务端权威模拟的具体范围，以及哪些判定必须在服务端执行。
- tick rate、状态同步频率和消息粒度。
- 是否需要延迟补偿，以及采用何种实现。
- 是否引入数据库、Redis、账号系统和长期战绩。
- 部署区域、实例规格、扩容方式、监控和备份。
- 并发房间数、单房间人数和目标网络质量指标。

## 10. 验收方向

- 多名玩家可稳定创建、加入、离开和结束房间。
- 房间规则与关键战斗结算由服务端校验，客户端不能直接篡改结果。
- 在约定网络条件下，玩家位置和战斗状态同步稳定。
- 断线、重连、异常消息和房间销毁均有可验证行为。
- 压测结果覆盖目标房间人数与并发房间规模。

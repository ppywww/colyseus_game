# 01｜当前版本问题与主菜单视觉方向

> 状态：主菜单方向已完成口头讨论，等待视觉预览确认  
> 范围：当前版本体验问题、主菜单视觉方向与基础交互流程  
> 原则：本文件记录已讨论的产品方向。美术细节由设计先提出方案，再通过预览图确认；本阶段不修改游戏代码。

## 1. 项目当前主要问题

### 1.1 地图与场景

- 当前地图结构和整体观感不符合预期。
- 核心场景方向为一栋房子、一个院子，以及花园等户外区域。
- 主菜单画面中，四个角色位于花园内，呈现追逐、互动或各自有特点的动态动作；房子作为后方主要背景。
- 房屋、庭院、花园的具体结构、构图和空间比例由设计先行判断，以整体美观、空间层次和游戏辨识度为准。

### 1.2 角色与视觉表现

优先展示以下四个原创角色。角色物种可以是猫、鼠、狗，但造型应有独立原创辨识度，不照搬任何现有影视或游戏角色。

| 暂定称呼 | 外形与性格方向 | 专属装备 / 定位 |
|---|---|---|
| 高手猫 | 蓝色、高瘦、气质冷静 | 水枪 |
| 圆小鼠 | 棕色、矮小圆润、古灵精怪 | 弹珠枪 |
| 方块狗 | 身形方正、厚重、肌肉感强 | 大型盾牌，偏近战 |
| 细长黑猫 | 身形细长、敏捷灵活 | 玩具狙击枪，偏远程 |

设计要求：
- 用户提供的角色参考图是造型基础。设计可在此基础上优化比例、细节、材质、服装和表情，使角色更适合游戏画面。
- 角色动作由设计自行安排，优先体现四者不同的性格和战斗定位，并形成活泼、有故事感的群像。
- 装备以用户明确指定的类型为准；参考图中不符合设定的武器应替换或重新设计。
- 具体装备造型可由设计发挥创意，但应符合角色定位、整体世界观和卡通玩具化的视觉方向。

### 1.3 道具与战斗反馈

- 当前枪械射击体验不理想，需要后续单独讨论射击反馈、准星、命中表现和操作手感。
- 手榴弹的落点表现和视觉反馈不理想，需要重新设计。
- 道具需要与角色定位和整体卡通世界观协调，避免风格割裂。
- 本节先记录问题，不在本阶段规定战斗数值或实现方式。

### 1.4 UI 与房间流程

- 当前 UI 的整体布局和视觉表现不符合预期，需要重新设计。
- 游戏运行在浏览器中，是桌面端网页游戏；不是手机游戏，也不是手机横屏 UI。
- 游戏不采用复杂的玩家成长系统。玩家进入游戏后可以直接使用或自行修改一个名字，并使用系统提供的随机头像。
- 不需要展示经验等级、经验条等玩家成长信息。
- 主菜单的核心操作是“创建房间”和“加入房间”。
- 设置页面目前明确需要：鼠标灵敏度、准星调节、声音与音效音量调节。

## 2. 主菜单参考与布局方向

### 2.1 参考图的使用方式

- 用户提供的第一张主菜单截图用于参考主菜单信息布局和画面组织方式。
- 用户提供的第二张角色图用于参考四个原创角色的造型基础。
- 参考图用于传达构图、角色和设计意图，不要求逐项照搬。
- 主菜单背景为房子、院子和花园；四个角色在花园中展示各自的动作与专属装备，房子位于后方。
- 整体美术风格、UI 细节、色彩、字体、材质和光影由设计先行确定，优先保证精致度、可读性和桌面端游戏体验。

### 2.2 初步布局

以**浏览器桌面端**为目标，按常见电脑显示器的宽屏比例进行设计，不采用手机端布局。

- **左上角：玩家信息**
  - 显示系统随机分配的默认头像。
  - 显示玩家名称，玩家可以自行编辑。
  - 不显示经验等级、经验进度等成长信息。
  - 头像与名称区域简洁，不抢占主视觉。

- **画面中心偏左：角色展示**
  - 展示高手猫、圆小鼠、方块狗、细长黑猫四个原创角色。
  - 四个角色各自持有对应的专属装备。
  - 角色位于花园中，以追逐、互动或其他有表现力的动作呈现。
  - 角色整体偏左，为右侧主要操作入口留出清晰空间。

- **画面右侧：主要房间操作**
  - 设置两个醒目的大尺寸纵向长方形按钮，采用上下排列：
    1. 创建房间
    2. 加入房间
  - 因主菜单核心入口只有这两个，按钮应足够大、突出、易识别。
  - 按钮的具体视觉样式由设计决定。

- **设置入口**
  - 保留清晰可见的设置入口。
  - 设置页面至少包含以下项目：
    - 鼠标灵敏度调节；
    - 准星调节，需提供较细致的自定义能力；
    - 声音与音效音量调节。
  - 准星的具体可调参数由设计提出合理方案，再通过设置页预览确认。

- **不需要的内容**
  - 不沿用参考图左侧整组纵向功能按钮。
  - 不擅自加入排行榜、活动中心、商城、经验等级、角色成长等未要求的系统入口。

### 2.3 主菜单角色选择（已确定方向）

- 主菜单同时承担角色选择功能，玩家无需进入独立选角页面。
- 花园中的四个角色既是场景主视觉，也是可交互的角色选择对象；玩家点击角色即可选中。
- 当前选中角色应有清晰但不突兀的视觉反馈，例如轮廓高亮、脚下标记、轻微镜头强调或专属待机动作。
- 选中角色后，玩家点击“创建房间”或“加入房间”，所选角色随玩家进入对应流程。
- 不新增独立的强制选角页面，避免打断主菜单到房间的操作流程。


### 2.4 角色选择动效与交互（已确定）

- 四个角色各自脚下常态显示一个奶酪造型的选择标记，作为角色选择器的视觉元素。
- 玩家点击某个角色时，奶酪标记以平滑、连贯的动画移动到该角色脚下，明确表示当前选择已切换。
- 被选中的角色同步放大，形成清晰的视觉焦点；未选中的角色恢复正常展示比例。
- 奶酪标记的移动与角色放大应作为同一次选择反馈协调播放，避免两个动作脱节。
- 选择反馈应有适度缓动和短暂的强调感，避免夸张弹跳、长时间动画或影响继续点击。
- 玩家可以反复点击不同角色切换选择；动画过程中也应保持交互响应，避免界面卡住。
- 初始进入主菜单时应有一个默认选中角色，奶酪标记和角色放大状态保持一致；默认角色可由系统指定，不要求固定某一个角色。
- 角色被选中后，后续点击“创建房间”或“加入房间”均携带当前选择的角色。

## 3. 房间入口与页面流程

### 3.1 创建房间

- 点击主菜单“创建房间”后，进入独立的创建房间页面或等待界面。
- 该页面用于完成创建房间相关操作，并在创建后进入房间等待状态。
- 具体房间参数、页面字段和等待界面细节后续再设计。

### 3.2 加入房间

- 点击主菜单“加入房间”后，进入独立的房间列表页面。
- 玩家在列表中选择房间并加入。
- 房间列表的筛选、刷新、房间信息展示等细节后续再设计。

### 3.3 进入游戏

- 创建房间和加入房间是两条不同的前置流程。
- 两条流程最终都汇入同一个对局开始 / 进入游戏流程。
- 玩家进入房间时，默认沿用主菜单已选角色。
- 在房间等待阶段，玩家可以在对局正式开始前更换角色；角色变更应同步反映在房间玩家展示中。
- 对局开始后锁定本局角色，避免对局中途随意切换影响战斗规则。
- 本文暂不规定房间内部的完整交互和对局规则。

## 4. 主菜单视觉目标

1. **桌面端网页游戏体验**：适配浏览器中的电脑宽屏显示，不采用手机 UI 思路。
2. **角色是视觉中心**：四个原创角色及其专属装备是画面重点。
3. **场景有完整空间感**：前景花园、中景角色、后景房屋形成清晰层次。
4. **卡通但精致**：角色和场景可以活泼夸张，但造型、材质、光照和 UI 需要统一，避免粗糙或简陋。
5. **操作入口明确**：创建房间和加入房间是最醒目的两个操作。
6. **UI 细节完整**：按钮、文字、图标、边距、层级和交互状态都应经过设计，不以临时拼凑的默认控件代替正式 UI。

## 5. 设置页面范围

当前明确的设置范围如下：

| 设置项 | 当前要求 |
|---|---|
| 鼠标灵敏度 | 提供灵敏度调节 |
| 准星 | 提供细致的准星自定义调节 |
| 声音 / 音效 | 提供音量大小调节 |

准星可调节的具体维度（例如形状、大小、颜色、间距、透明度等）由设计先提出完整且合理的方案，再通过设置页视觉预览确认；表中示例不代表用户已经逐项指定。

## 6. 当前阶段的交付方式

当前优先完成主菜单视觉预览，再继续细化 PRD；不进入代码修改阶段。

预览图重点验证：

- 桌面端浏览器宽屏构图是否合适；
- 房子、院子、花园的空间层次和比例；
- 四个原创角色是否符合参考图的造型方向；
- 四个角色是否分别使用水枪、弹珠枪、大型盾牌和玩具狙击枪；
- 角色动作是否生动，整体是否形成有趣的群像；
- 左上角头像与可编辑名称是否简洁；
- 右侧上下排列的两个大尺寸纵向按钮是否醒目；
- 设置入口是否清晰；
- 整体 UI 是否精致、统一，并符合桌面端 FPS 网页游戏的使用场景。

设计可以在不改变已明确需求的前提下加入合理创意。新增功能、玩家系统或角色设定不能擅自当作已确认需求。
